# 三秦巴士 / 唐生出行 定制巴士票务系统重建方案

> 调研日期：2026-11-12  
> 调研对象：https://www.ylxweb.com/admin.html（车队 `sqbs`，只读）  
> 目标框架：https://github.com/xinnix/loom  
> 本方案不含任何对现有系统的写操作；所有数据均来自只读页面与只读接口。

---

## 1. 结论摘要

### 1.1 现状判断

现有系统是**广州亿路航软件有限公司「亿路行」SaaS 的租户端**，前端为 ExtJS 4 单页应用，后端为 Java `.do` + `action` 式 RPC 接口，按 `corpID` 做多租户隔离。系统覆盖票务、调度、包车、查询统计、营销、微信、财务、权限等完整链路，功能非常全，但技术栈老、交互密度高、数据与源码都不在自己手里。

截至 2026-11-12，`sqbs` 租户的只读数据快照：

| 指标         |    数值 | 说明                                                             |
| ------------ | ------: | ---------------------------------------------------------------- |
| 线路数       |   39 条 | 以校园定制班线为主，覆盖西安及周边院校/交通枢纽                  |
| 客户数       | 166,174 | 乘客账号/客户档案                                                |
| 订单数       | 162,502 | 历史累计订单                                                     |
| 运营账号     |   26 个 | 含总管理员、线路操作员、支援账号、小程序账号                     |
| 小程序 AppID |    5 个 | 小旋风校车、三秦校园BUS、唐生出行、凸凸巴士、唐生出行-西译直通车 |
| 已录入车辆   |    6 辆 | 后台车辆档案；实际运营车辆以调度为准                             |
| 单日班次样本 |  159 班 | 2026-11-13（周五）9 条有班次的线路汇总                           |

### 1.2 重建建议

建议以 **loom 为底座，重建为「单租户、多品牌小程序」的定制巴士票务平台**：

- 管理后台：React 19 + Refine + Ant Design 6，替换 ExtJS。
- 后端：NestJS + tRPC（管理端）+ REST（小程序）+ Prisma + PostgreSQL + Redis。
- 用户端：uni-app + Vue 3，一套代码编译多个微信小程序（按品牌/appid 出包）。
- 先做 **P0 买票核销最小闭环**（线路/站点/班次模板/班次/下单/微信支付/电子票/扫码核销），再做 **P0.5 退票改签与日报表**，最后做 **P1 营销与财务、P2 包车/旅游/通勤/合同报备等差异化模块**。

**本方案明确不做：**

- 不逐像素复刻 ExtJS 旧界面；保留业务语义，重做交互与信息架构。
- 不在 P0 做微服务拆分、多语言、多时区；先做模块化单体。
- 不在 P0 做港澳、救护、通勤、旅游、合同报备等 sqbs 当前隐藏的模块。
- 不替换微信生态；继续使用微信小程序、微信支付、公众号。
- 不做未经确认的多租户 SaaS；默认单租户多品牌，是否需要 SaaS 见第 15 节。

### 1.3 投入与周期（建议基线）

按 2–3 人工程团队（P0：1 后端 + 1 前端/小程序；P1/P2 可扩到 3 人）+ 0.5 产品/设计 + 0.5 QA 估算：

| 阶段            | 范围                                                                |     周期 | 可交付状态                                |
| --------------- | ------------------------------------------------------------------- | -------: | ----------------------------------------- |
| P0 买票核销闭环 | 线路/站点/班次模板/班次、下单、微信支付、电子票、扫码核销、订单查询 |   6–8 周 | 可在 1 个品牌、2–3 条线路上真实售票并核销 |
| P0.5 运营安全阀 | 退票、改签、已支付取消、简单日报表、短信/订阅消息                   |     2 周 | 可面对真实乘客公开推广                    |
| P1 营销与财务   | 卡券、积分、分销、月卡、充值、发票、保险、结算、公众号              | 10–12 周 | 具备完整运营与对账能力                    |
| P2 差异化与全量 | 包车、旅游、通勤、港澳、救护、合同报备、三方代售、全量迁移          | 10–14 周 | 功能对齐现有系统，完成全量切换            |

> 时间可与学校学期节奏配合：2026 年 11 月–2027 年 1 月完成 P0，2027 年 1 月下旬–2 月完成 P0.5 与试点；2027 年春季学期开学公开推广。P0 不迁移历史数据，试点线路手工建；全量迁移放到 P1。

### 1.3.1 方案取舍（为什么不是改造旧系统）

| 方案                           | 结论   | 原因                                                         |
| ------------------------------ | ------ | ------------------------------------------------------------ |
| A. 基于 loom 全栈重写（推荐）  | 采用   | 数据/源码自主可控，技术栈现代，能支持多品牌小程序与后续扩展  |
| B. 在亿路行系统上二次开发/换皮 | 不采用 | 源码与数据库不在自己手里；ExtJS 技术栈无法演进；受制于供应商 |
| C. 采购另一套 SaaS             | 不采用 | 仍然是数据锁定；难以做品牌化与差异化运营                     |
| D. 只做小程序、不管后台        | 不采用 | 排班、库存、退款、结算仍需后台；只做前端无法闭环             |

### 1.4 最大的三个风险

1. **数据迁移**：现有系统没有公开数据库导出能力，必须先解决 162,502 个订单、166,174 个客户、历史卡券/余额/月卡的完整导出与对账。
2. **微信生态多 appid / 多商户**：5 个小程序、不同品牌、可能不同支付商户号；loom 当前是单 appid + 单商户环境变量配置，需要改造成数据库配置。
3. **库存并发与财务准确性**：班次座位/站点配额、支付回调、退款、改签必须在一个事务模型里闭环，否则会出现超卖或账实不符。

### 1.5 最脆弱的假设

本方案成立的前提是：**能拿到旧系统的完整数据导出（至少订单、客户、卡券、余额、月卡可完整导出）**。如果拿不到，迁移只能靠后台 Excel/只读接口/人工补录，P0 上线时间至少增加 4–6 周，且历史余额/卡券存在无法完全对账的风险。

## 2. 调研方法与边界

### 2.1 调研方法

- 使用只读账号登录后台，逐项查看左侧导航、列表、表单、弹窗与配置项。
- 读取前端加载的 ExtJS 源码（`app/view/**`、`app/controller/**`、`app/app.js`、`app/view/CenterPanel.js`），还原页面字段、列表列、接口 action 与业务规则。
- 调用只读 `*.list` / `*.info` 接口获取租户级统计数据；未调用任何 `save`、`del`、`update`、`refund`、`buyTicket` 等写接口。
- 参考 loom 仓库的 README、AGENTS.md、Prisma schema、模块目录与微信支付实现，评估复用边界。

### 2.2 现有系统技术画像

| 维度     | 现状                                                                                        |
| -------- | ------------------------------------------------------------------------------------------- |
| 前端     | ExtJS 4.x 单页应用，`AM.view.*` 视图 + `Ext.data.Store` 数据层；桌面端优先，无响应式        |
| 后端接口 | `/api/admin.do?action=xxx` 形式的 action RPC；部分旧接口为 `/admin/xxx.do`、`/adminweb/xxx` |
| 多租户   | 登录参数 `corpID`（车队），数据按 corp 隔离；前端存在大量 `curConfig.corpID` 条件分支       |
| 鉴权     | `User-Token` + `Ts` + `X-Ca-Nonce` 请求头；登录后加载 `operator.info`                       |
| 金额     | 数据库/接口以「分」为单位（`ticket_price_fen`、`total_fee`、`bottom_price_fen` 等）         |
| 前端规模 | 约 90 个业务视图 JS 文件、3.3MB 源码；单文件最大 201KB（车辆管理）                          |
| 业务重心 | 校园定制班线（学校—地铁站/火车站/机场），多班次、多站点、低票价、高频次                     |

### 2.3 需要特别说明的边界

- 本方案只覆盖 **sqbs 租户实际启用的功能**，并对隐藏模块给出可选规划。
- 现有系统的「港澳线路、救护管理、通勤管理、旅游线路、合同报备、信息导入」等模块在 sqbs 账号下被隐藏，说明当前业务未使用；新系统先不做，避免把未验证的复杂度带进 MVP。
- 现有系统车辆档案只有 6 辆，但新闻报道/实际运营车辆更多；车辆管理需要按「运营车辆」与「档案车辆」分开设计，不能只依赖车辆列表的数据量判断业务规模。

### 3.2 核心票务模块详解

#### 上下车点（Manage.Location）

- 按线路维护上车站点（`locationType=0`）与下车站点（`locationType=2`）。
- 字段：站点名称、详细地址、经纬度、排序、站点类型、自定义区域、站点 code、城市/区域、站点电话、站点图片、状态。
- 支持地图选点、关键词搜索、拖拽排序、按线路复制站点、批量删除、批量设置自定义区域、导入/导出 Excel。
- 区域（Area）支持电子围栏：在地图上绘制多边形，设置可选区/不可选区，用于线路范围与站点归属。

#### 班次模板（Manage.Template）

- 按线路维护可复用的班次模板：班次名称、始发时间、随车电话、车辆、总放票数、儿童票数、携童余数、定价规则、支付方式（上车支付/微信支付）、代金券、会员优惠、发班周期（周一至周日）、排序、标签、分享优惠、微信支付减免、特价票。
- 定价规则支持：按上车地点票价、按下车地点票价、区间票价（上下车站点组合）。
- 支持批量修改票价、提前/延迟发车、复制模板等。
- 模板是排班的「母版」，实际班次（Trip）由模板 + 日期生成。

#### 班次管理（Manage.Ticket）

- 左侧选线路，中间选日期，右侧显示当天班次列表。
- 支持按模板批量排班、批量修改票价/放票数、停售/开启、停班/取消发车、提前/延后发车。
- 每个班次可下钻到：座位表、订单列表、车票列表、上下车站点票价、站点放票数、标签、班次图片、分享优惠、微信支付减免、特价票。
- 班次状态：正常/停售/停班（取消发车）/已结束等。
- 支持“混检”场景：乘客可检票至其他班次，系统统计混检票数/金额。

#### 实时班次（Manage.Interval）

- 面向调度/现场：按线路/日期/班次/车牌/司机查询实时班次。
- 查看每班次订票人数、余票、座位表、订单、上下车站点、状态。
- 支持修改班次信息、调整放票数、派车/派司机、发送通知。

#### 订单记录（Manage.OrderList）

- 多维筛选：线路、乘车日期、班次、上下车点、车牌、司机、操作员、支付状态、签到状态、订单类型、来源、供应商、渠道、手机号、姓名。
- 订单详情：订单 ID、微信 openid、联系人、手机号、身份证、人数、儿童、乘车日期、班次、上下车点、优惠、操作员、支付方式/状态、创建时间、渠道、短信/微信内容。
- 操作：修改备注/手机号、退款（全退/按比例/部分退）、改签、派单、通知乘客（公众号/短信）、打印、导出 Excel、导入 Excel、导出抖音卡券关联订单。
- 订单状态（旧系统）：支付状态 0 未支付、1 已支付、2 已退款、3 待支付、4 已关闭、20 退款中、21 部分退款、23 延迟退款中；签到 0 飞机、1 未签到、2 已签到；类型 0 普通、2 双程、3 寄货、4 问询、5 取消、6 改签。
- 支付方式：0 上车支付、1 线上支付、2 余额支付；渠道：后台录入、网上订票、公众号、小程序、司机端、抖音、API、携程等。

### 3.5 现有系统的真实使用特征

- **校园班线是核心**：39 条线路中绝大多数是“学校—地铁站/火车站/机场”的往返线；单日 159 个班次、单班次最高 500 个放票数（虚拟座位，不选座）。
- **低票价、高频次**：常见票价 7.9 元、13.9 元；支付以微信为主，存在上车支付。
- **多品牌运营**：5 个小程序覆盖不同校区/合作方，说明系统必须支持“一套后台、多品牌前端”。
- **多操作员、按线路分权**：26 个账号中有大量按线路命名的角色/账号，权限需要按线路和车辆做数据范围隔离，而不是简单“管理员/普通用户”。

## 4. 现有系统的主要问题

| 问题                 | 具体表现                                                                         | 重建后的处理                                       |
| -------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------- |
| 技术栈老化           | ExtJS 4 已停止维护；页面大量 `Ext.define` 内联模型/Store，单文件 200KB           | React + Refine + AntD，组件化、类型安全            |
| 前后端契约弱         | `action` 字符串 RPC，字段命名混用 `ID/id`、`total_fee/totalFee`，无 OpenAPI/类型 | tRPC 端到端类型 + Zod 校验；管理端/小程序分协议    |

## 5. 目标系统总体设计

### 5.1 设计原则

1. **票务交易为核心**：先保证“查得到、买得成、退得了、检得进、对得平”，再做营销和增值。
2. **配置驱动，不写死客户差异**：品牌、线路、票价、退改规则、支付方式、页面文案都配置化。
3. **单租户、多品牌**：一个运营主体（sqbs）下支持多个小程序品牌；不为每个品牌复制一套后台。
4. **金额用分、时间用 UTC、业务日期用 Asia/Shanghai**：避免浮点与跨时区问题。
5. **所有写操作可审计、可回滚**：订单、退款、改签、结算全部留操作日志与前后值。
6. **先能用、再替换**：P0 可先在部分线路/品牌试点，与老系统并行，确认无误后全量切换。

### 6.4 状态机

**订单状态**：

```
DRAFT → PENDING_PAYMENT → PAID → COMPLETED
   │          │              ├→ PARTIALLY_REFUNDED → REFUNDED
   │          │              └→ REFUNDING → REFUNDED
   │          └→ CLOSED（超时未支付/取消）
   └→ RESERVED（上车支付）→ PAID（上车支付完成）
```

**票状态**：`UNUSED → CHECKED_IN`；`UNUSED → REFUNDED`；`UNUSED → CANCELLED`。  
**支付状态**：`UNPAID → PENDING → PAID → PARTIAL_REFUND → REFUNDED`；`PENDING → FAILED/CLOSED`。  
**班次状态**：`DRAFT → ON_SALE → STOPPED → DEPARTED → COMPLETED`；`CANCELLED` 可从中途进入。

> 旧系统把「支付状态、签到状态、订单类型」混在多个字段里；新系统必须拆成上述四套状态机，避免组合爆炸和报表口径不一致。

## 7. 核心业务流程

### 7.1 排班流程

1. 运营在「班次模板」为线路维护每日/每周班次模板（时间、车辆、票价规则、放票数）。
2. 在「排班日历」选择日期范围，按模板批量生成 `Trip` 与 `TripStop`。
3. 系统按模板生成每个班次的站点票价、站点配额；总库存 = 班次 `totalSeats`。
4. 运营可对单班次调整票价、放票数、车辆、司机、状态（停售/停班）。
5. 发车前按配置停止售票；发车后班次自动进入 `DEPARTED/COMPLETED`。

### 7.2 乘客购票流程

```
打开小程序 → 微信静默登录 → 选出发地/到达地/日期
→ 班次列表（余票/票价/标签） → 选班次
→ 选上/下车点 → 选票数/儿童数 → 填写乘车人/手机号
→ 选优惠券/余额/月卡 → 下单（服务端锁库存）
→ 微信支付 → 支付回调 → 出票（每票一个二维码/检票码）
→ 订阅消息（发车前提醒）
```

关键控制点：

- 下单接口必须带 `Idempotency-Key`，防止重复点击生成两单。
- 库存预占与支付超时释放：下单锁库存 15 分钟；超时自动取消并释放。
- 价格只以服务端计算为准，客户端传入的价格仅用于展示校验。
- 支付回调必须验签、幂等；以 `transactionId` 唯一约束防重复入账。
- 出票后立即生成票号/检票码；小程序订单详情直接展示二维码。

### 7.3 后台电话预订流程

1. 操作员选择日期、线路、班次、上下车点、人数。
2. 输入联系人手机号/姓名，选择来源（后台录入/司机端/API）、备注、短信模板。
3. 选择支付方式（上车支付/线上支付/余额支付），提交订单。
4. 系统按与服务端相同规则计算票价、锁库存、生成订单/票。
5. 可发送短信/公众号消息；支持打印小票/导出。

> 后台预订与小程序购票必须共用同一套价格计算、库存锁、订单状态机，不允许两套逻辑。

### 7.4 退票流程

1. 乘客在订单详情点「退票」或客服在后台发起。
2. 系统按线路退票规则计算：发车前 X 分钟停止退票、按时间阶梯收取手续费。
3. 创建退款单，冻结对应票；调用微信退款（或余额退回）。
4. 退款成功后：票状态 `REFUNDED`、订单状态 `PARTIALLY_REFUNDED/REFUNDED`、释放库存（发车前）、记录退款流水。
5. 退款失败：进入人工处理队列，展示失败原因，支持重试/线下退款登记。
6. 所有退款操作写入 `OperationLog`，记录操作员、金额、原因、原订单。

### 7.5 改签流程

1. 校验改签规则（发车前 X 分钟、仅可改签一次、改签后不可退等）。
2. 选择新班次/日期/上下车点，计算新旧票价差。
3. 新班次锁库存 → 旧票释放 → 生成新票/新二维码；差价在线支付或原路退回。
4. 改签成功后旧票状态 `CANCELLED`，新票 `UNUSED`，订单记录 `OrderChange`。
5. 改签失败必须回滚库存与支付。

### 7.6 检票流程

1. 检票员打开小程序「检票」页，扫码或输入 6 位检票码。
2. 服务端校验：票存在、属于当前班次/日期、状态 `UNUSED`、未过发车时间（可配置宽限）。
3. 原子更新 `Ticket.status=CHECKED_IN` + 写入 `CheckIn`；重复扫码返回「已检票」及时间/操作员。
4. 检票员可查看班次乘客列表、已检/未检人数；支持手工补检、取消检票（权限控制）。

### 7.7 结算与对账流程

1. 每日凌晨定时任务汇总前一日订单：支付、退款、手续费、净收入。
2. 按线路/班次/供应商/代售渠道生成结算单。
3. 拉取微信支付交易账单，逐笔匹配 `transactionId/outTradeNo`；差异进入「异常池」。
4. 财务确认结算单 → 打款 → 上传凭证 → 状态流转（待核对/已核对/已打款/关闭）。
5. 所有报表可导出 Excel；金额与订单明细可下钻。

- 弱网：列表/订单详情做缓存与骨架屏；支付结果轮询 + 主动查单。
- 兼容：微信基础库最低版本、iOS/Android 差异、隐私协议弹窗。

## 10. 权限、安全与合规

### 10.1 账号与登录

- 管理端：账号密码 + 可选微信扫码登录；密码强度策略、登录失败锁定；支持 IP 白名单（P2）。
- 小程序：微信静默登录 + 手机号授权；不使用密码。
- 管理员与乘客身份完全隔离（loom 的 `type: admin/user` JWT 机制）。
- 敏感操作二次验证（退款超过阈值、导出客户数据）。

### 10.2 数据安全

- 身份证号、手机号、openid、微信 secret、支付密钥加密存储；身份证号展示脱敏（`110***********1234`）。
- 数据库备份：每日全量 + WAL 归档（PITR 7 天）；备份异地存储。
- 导出文件加水印/有效期；下载记录审计。
- 支付证书/私钥放 KMS/Secret Manager，不提交仓库。
- 所有写接口记录 `OperationLog`（操作人、IP、UA、前后值）。
- 防重放：`X-Ca-Nonce`/`Idempotency-Key`；支付回调验签。

### 10.3 合规

- 微信小程序隐私协议、用户授权、手机号使用说明。
- 个人信息保护法（PIPL）：最小必要收集、可注销、可导出、数据保留期限。
- 发票/保险/包车报备等涉及资质与第三方接口，按业务需要单独合规评估。

## 11. 数据迁移与上线方案

### 11.1 数据源

优先顺序：

1. **向亿路行申请完整数据库导出**（最佳）：拿到 MySQL 全量备份/CSV，含订单、票、客户、卡券、余额、月卡、线路、站点、班次等。
2. **后台导出 Excel**：订单记录、客户管理、卡券列表、月卡等页面有导出功能；可导出后做 ETL。
3. **只读接口抽取**：对无导出功能的小表，用只读 `*.list` 接口分页拉取（仅限迁移工具，不写入）。
4. **人工补录**：极少数配置（短信模板、首页 Banner、公告）可人工重建。

### 11.2 迁移步骤

1. **建 staging 库**：PostgreSQL 中建 `legacy_*` 原始表，保留旧字段与旧 ID。
2. **抽取**：按表/分页导出 CSV/JSON，校验行数、金额汇总。
3. **清洗与映射**：
   - 旧 `line.ID` → `Line.legacyId`；旧 `location.ID` → `Station/LineStation.legacyId`。
   - 旧 `basic_interval.IntervalId` → `ScheduleTemplate.legacyId`。
   - 旧 `interval.IntervalId` → `Trip.legacyId`。
   - 旧 `order.BusNum` → `Order.orderNo`（保留原单号）或 `legacyOrderNo`。
   - 旧 `order_ticket.ticketId` → `Ticket.legacyTicketId`。
   - 旧 `customer.id` → `User.legacyCustomerId`。
   - 旧 `openid` + `appid` → `UserIdentity`。
   - 旧卡券/月卡/余额 → 对应账户表，保留 `legacyId`。
4. **导入**：按依赖顺序导入（城市→线路→站点→模板→班次→用户→订单→票→支付→退款→卡券→月卡→结算）。
5. **对账**：按日/线路/支付方式核对订单数、票数、金额、退款、手续费；差异清单逐条处理。
6. **试运行**：选 1–2 条线路/1 个品牌，新旧系统并行 2–4 周，双写或只读比对。
7. **正式切换**：低峰期冻结旧系统写入 → 最后一次增量同步 → 切换小程序 API 域名/后台入口 → 观察 7 天 → 旧系统转只读归档。

### 11.3 迁移映射表（核心）

| 旧系统                                    | 新系统                                   | 备注                                                 |
| ----------------------------------------- | ---------------------------------------- | ---------------------------------------------------- |
| `line`                                    | `Line`                                   | `lineName`/`showName` 拆分内部名/展示名              |
| `location`                                | `Station` + `LineStation`                | 旧系统同站点按线路重复，新系统拆分物理站点与线路站点 |
| `basic_interval`                          | `ScheduleTemplate`                       | 保留星期、时间、票价规则                             |
| `basic_address` / `basic_get_off_address` | `TemplateStop`                           | 模板上下车点/票价                                    |
| `interval`                                | `Trip`                                   | 旧 `IntervalId` 保留为 `legacyId`                    |

### 11.4 迁移验收标准

- 订单总数、票总数、客户数、线路数、站点数与旧系统一致（允许明确说明的重复/合并差异）。
- 按日/线路/支付方式汇总金额与旧系统差异 ≤ 0.01 元。
- 抽样 100 个历史订单，详情、票状态、退款金额完全一致。
- 卡券/月卡/余额可用余额一致，且有明细可追溯。
- 切换后 7 天内无 P0/P1 数据事故。

## 12. 实施计划

### 12.1 阶段划分

#### P0：买票核销最小闭环（6–8 周）

**目标**：只跑通「乘客买票 → 微信支付 → 电子票 → 检票员扫码核销」，不做营销、财务、多品牌、车辆调度等非核心功能。详细执行清单见《P0 买票核销最小闭环方案》。

**交付物**：

- loom 项目初始化：`apps/api`、`apps/admin`、`apps/miniapp`；关闭 `web/landing`。
- Prisma schema（P0 表）+ 迁移 + seed。
- 管理端：单管理员登录、线路、上下车点、班次模板、班次生成/管理、订单列表/详情、核销记录、核销员账号、单小程序/单商户配置。
- 小程序：微信登录/手机号、线路列表、班次列表/详情、选站、下单、微信支付、我的订单、电子票二维码。
- 核销端：核销员登录、扫码/核销码核销、防重复核销、核销记录。
- 支付：微信 JSAPI + 回调 + 查单（不做退款）。
- 测试：单元 + 集成 + E2E + 并发压测。

**验收**：

- 管理员可建线路/站点/班次模板，并生成未来 7 天班次。
- 乘客可完成“选线路→选班次→选站→下单→支付→出示电子票”。
- 核销员可扫码核销；同一张票第二次核销被拒绝。
- 50 并发购买同一班次不超卖；支付回调重复投递不重复出票。
- 试点 2–3 条线路完成至少 50 笔真实订单。

#### P0.5：运营安全阀（2 周）

**交付物**：

- 退票（全额/按时间阶梯手续费）、改签（一次改签/差价处理）、已支付订单取消。
- 简单日报表（每日订单数/票数/金额）。
- 订单确认短信/订阅消息。

**验收**：公开推广前，乘客可自助退票/改签，客服可在后台处理异常订单；日报表与支付流水一致。

#### P1：营销与财务（10–12 周）

**交付物**：

- 卡券池/优惠券、积分、会员/月卡、充值/余额、分销员/佣金。
- 发票、保险、短信群发。
- 公众号管理（菜单、图文、关键词、自动回复、用户、图片）。
- 渠道二维码/收款二维码。
- 财务：每日票款、线路/班次汇总、交易数据、结算单、微信账单对账、司机成本申报。
- 客户反馈、验票统计、操作日志。
- 多品牌小程序完整支持（5 个 appid 构建/发布）。
- 数据迁移全量演练。

#### P2：差异化与全量（10–14 周）

**交付物**：

- 包车管理、旅游线路、通勤管理、港澳线路、救护管理。
- 合同报备、电子路单、派车管理、运输企业、司机账号、旅游合同（如需要对接交通主管部门）。
- 三方代售、订单来源、信息导入/自动下单、临时群聊、乘车信息、打印机管理、IP 白名单。
- 多租户 SaaS（如决定对外输出）。
- 旧系统全量数据迁移、切换、旧系统只读归档。
